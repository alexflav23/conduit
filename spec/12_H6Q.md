# 12 — H6Q Forecasting Subsystem (full depth)

H6Q is Hypervolt's bottom-up demand forecast: **many account owners, distributed across regions and timezones, each forecasting their own accounts every week**, with Conduit capturing every estimate (by whom, when, for which account) and **auto-rolling it up** to the H6Q hierarchy with no central re-keying. This document is the build-grade deep-dive that doc 10 §A scheduled — the subsystem outgrew the `§H6Q` in doc 04. It supports **build milestone M11** (doc 07).

**This doc REFERENCES and EXTENDS — it does not redefine.** The storage tables live in **doc 02 §K** (`forecast_scenario`, `forecast_cycle`, `forecast_submission`, append-only `forecast_entry`, `forecast_accuracy`, `pipeline_coverage`, `sell_through`); the load-bearing algorithms live in **doc 04 §H6Q** (cycle open/submit, coverage, sell-through, sources); the events in **doc 03 (Forecast)**; the REST surface in **doc 06 (H6Q)**; data-layer projection in **doc 05 §3**; the Flutter capture screens in **doc 08 §3 (S3–S6)**. Where this doc adds a column, an event, an endpoint or an algorithm beyond those, it is called out as **NEW** and the home table/registry it extends is named. Cross-references to other docs are given as `doc NN §X`.

Conventions per doc 00: PostgreSQL 16 types; money is `NUMERIC(18,4)` + `CHAR(3)`; `BigDecimal`, `HALF_UP` at presentation only; UTC instants (`TIMESTAMPTZ`), fiscal/period assignment is a projection (doc 14 §2); transactional outbox + idempotent-on-`event_id` consumers (doc 03); pseudocode is language-neutral, implemented in Scala 2.13/cats-effect. Group presentation currency = USD.

## 1. Scope, principles & boundaries

### 1.1 What H6Q is
A continuously-captured, replayable, **materialised** picture of expected demand vs committed supply, assembled from:
- **Manual bottom-up estimates** — every account owner forecasts each account they own, per SKU / month / scenario, every weekly cycle (the dominant source);
- **Weighted pipeline** — open `deal` lines × `pipeline_stage.probability_pct` (doc 02 §C);
- **Committed/actual** — `order_line.qty_dispatched` (sell-in) and `activation` (sell-through);
- **Hyperview** — Prophet retail forecasts landing as `forecast_entry.source='hyperview'` (doc 04 §H6Q, §6 here).

These compose into **coverage** (how much of the forecast is covered by shipped + weighted pipeline), **WoW** movement, **sell-through / overhang**, and **accuracy** (estimate vs actual per owner).

### 1.2 Principles (carried from doc 04 §H6Q / doc 07 Decisions)
1. **Distributed capture, no re-keying.** Owners submit from mobile/tablet/web, async across timezones; rollup is automatic and event-driven.
2. **Append-only truth.** Every estimate is retained with author + timestamp; a revision is a new `forecast_entry` row with `superseded_by` set on the prior (doc 02 §K) — never an update. This is what makes accuracy scoring honest.
3. **Materialised, replayable projections.** `pipeline_coverage`, `sell_through`, `forecast_accuracy` are rebuilt by consumers of `forecast.*`, `order.*`, `dispatch.*`, `activation.recorded`, `crm.deal.*`. No cross-system cache; a projection rebuild from the event log reproduces them exactly (doc 01 §3a).
4. **Catalogue-live.** The capture surface reads the live catalogue (`GET /catalogue`, doc 06); a new `product_variant` is forecastable the moment it exists — no schema or config change (doc 02 §D).
5. **Layer-aware everywhere.** The same board composes from grants: `volume` sees units/coverage %, `commercial` adds revenue, `profitability` adds margin/GP (doc 05 §3). Capture is volume-only.
6. **Dual aggregation that reconciles.** Every figure rolls up **by branch** (org hierarchy) *and* **by sales agent** (ownership) from the same atomic rows — the two views must tie.

### 1.3 Boundaries (what H6Q is NOT)
- **Not a planning engine.** Replenishment/net-requirement math lives in Supply (doc 02 §H `replenishment_suggestion`, doc 04 §ATP). H6Q feeds future demand (scheduled tranches + forecast) into it; it does not compute purchase suggestions.
- **Not Prophet.** Hyperview runs Prophet as a **separate upstream project** (doc 07 Decisions); H6Q ingests its output as a source. H6Q never trains or runs a model.
- **Output-only export.** The spreadsheet export (`GET /h6q/export`) is a read projection; nothing is ever imported from a spreadsheet (no re-keying — principle 1).
- **No money creation.** H6Q reads commercial/profitability figures (from resolved pricing + batch cost) for display under the relevant layer; it posts nothing to the ledger.

## 2. The weekly cycle engine

### 2.1 Cadence, windows & timezone-agnosticism
A `forecast_cycle` (doc 02 §K) is the weekly capture window: `code` (ISO week, e.g. `2026-W23`), `period_start`/`period_end` (DATE), `cadence` (default `weekly`, configurable), `status` (`open`/`closed`). The cycle window is the **submission window** — *when an owner may submit* — and is distinct from `forecast_entry.period_month`, which is *the horizon month being forecast*. One cycle captures estimates for many future months.

**Timezone-agnostic** (doc 02 §K): a submission is valid whenever it lands within `[period_start, period_end]`. There is no per-owner local deadline; the window is evaluated against the cycle bounds, not the owner's clock. `period_start`/`period_end` are DATE bounds interpreted inclusively at the cycle's reference TZ (the group reporting TZ, doc 14 §2) purely to decide membership — the act of submitting carries the server `submitted_at` UTC instant, and lateness is `submitted_at`-vs-`period_end` only for reporting, never to reject.

**Cadence is data.** `cadence` on `forecast_cycle` drives the scheduler's next-window computation; `weekly` is the seed. Switching to fortnightly/monthly is changing the cadence value + the scheduler cron — no code (mirrors `commission_period.cadence`, doc 02 §J).

### 2.2 Open: scheduler + outstanding-submission generation
Driven by a scheduler (doc 01); extends doc 04 §H6Q `openCycle` with concurrency, idempotency and skip semantics:

```
openCycle(asOf, cadence='weekly'):                       // scheduler-triggered, idempotent on cycle code
  code = isoWeek(asOf)                                   // e.g. "2026-W23"
  cycle = upsert forecast_cycle(code, period_start=startOfIsoWeek(asOf),
                                period_end=endOfIsoWeek(asOf), cadence, status='open')
  if cycle existed AND cycle.status != 'open': return    // never reopen a closed cycle (append a new one)
  owners = DISTINCT users u WHERE exists party p
              WHERE 'forecastable' = ANY(p.roles)        // doc 02 §C party.roles
                AND (p.account_manager_user_id = u.id OR p.owner_user_id = u.id)
                AND p.status = 'active'
  for owner in owners:
     for acct in forecastableAccountsOwnedBy(owner):     // see §2.3
        // INSERT ... ON CONFLICT (cycle_id, forecaster_user_id, company_id) DO NOTHING  → idempotent re-open
        insert forecast_submission(cycle, owner, company=acct, status='outstanding', device=null)
  emit forecast.cycle.opened
  // notification consumer fans out a per-owner nudge (§2.6)
```

- **Idempotent:** re-running `openCycle` for the same ISO week is a no-op on existing submissions (`ON CONFLICT DO NOTHING`) — safe under scheduler retries / replay.
- **Replayable:** the outstanding set is a deterministic function of cycle + ownership-at-open. The set is **frozen at open** for the "who owes this week" view; ownership changes mid-cycle are handled in §2.5.

### 2.3 `forecastableAccountsOwnedBy(owner)` — what an owner gets asked for
```
forecastableAccountsOwnedBy(owner):
  return party p WHERE 'forecastable' = ANY(p.roles)
     AND p.status='active'
     AND (p.account_manager_user_id = owner.id OR p.owner_user_id = owner.id)
     // BRANCH-LEVEL CAPTURE: a wholesaler master with branches that each carry their own
     //   account_manager_user_id surfaces the BRANCHES to their owners, not the master.
     //   A leaf account (no children) surfaces itself. Rule:
     //   - if p has forecastable children → exclude p (it rolls up from branches), include the children
     //   - else → include p
```
So a CEF *master* with 40 branch parties (each `account_manager_user_id` set) produces 40 outstanding submissions to the relevant branch owners; the master line is **derived by rollup** (§4), never captured directly. A standalone installer account produces one submission to its owner. This is exactly the "account (or branch)" semantics on `forecast_submission.company_id` (doc 02 §K).

### 2.4 Close
```
closeCycle(cycle):                                       // scheduler at period_end, or manual (admin)
  require cycle.status == 'open'
  cycle.status = 'closed'
  // outstanding submissions are NOT deleted — they remain status='outstanding' as the record of who didn't submit
  emit forecast.cycle.closed
```
Closing **does not** mutate outstanding submissions: the residual `outstanding` rows are the audit of non-participation and feed accuracy/coverage-of-forecasters reporting. A closed cycle is never reopened — the next window is a new `forecast_cycle`. Submissions arriving after close (offline queue draining late, doc 08 §0 Offline) attach to the **then-current open cycle** if their `submitted_at` falls in it, else are rejected with `409 cycle_closed` and re-queued for the open cycle (§3.3).

### 2.5 Mid-cycle ownership change
If an account is reassigned (`party.account_manager_user_id` changes) while a cycle is open:
- the existing `outstanding` submission for the old owner is set `status='skipped'` with `skip_reason='reassigned'` (NEW column, §2.7);
- a new `outstanding` submission is created for the new owner (same `ON CONFLICT` guard);
- `forecast_accuracy` attributes any already-submitted estimate to its **original** `forecaster_user_id` (append-only — the author of record never changes, doc 02 §K).

### 2.6 Owner notifications
The notification consumer (doc 10 §B Notifications model; events from doc 03) reacts to:
- `forecast.cycle.opened` → per-owner push/email: *"Forecast week {code} — {n} accounts due."* Deep-links to S3 (doc 08).
- A **closing-soon** reminder: a scheduler emits a derived nudge to owners with `outstanding > 0` at a configurable lead (e.g. 24h before `period_end`). (No new event type — reuses the notification consumer reading `forecast_submission.status` for the open cycle.)
- `forecast.cycle.closed` is informational; not user-facing by default.

Channels/templates/preferences are the notifications model's concern; H6Q only guarantees the **signal** (the event + the outstanding query) exists.

### 2.7 Cycle-engine schema deltas (NEW)
Extends **doc 02 §K** (additive, backward-compatible):

`forecast_submission` — NEW columns:
| column | type | notes |
|---|---|---|
| `skip_reason` | TEXT NULL | set when `status='skipped'` (`reassigned`/`no_demand`/`owner_skipped`) |
| `submitted_via_cycle_id` | UUID → forecast_cycle NULL | the cycle the submission actually landed in if it differs from `cycle_id` (late offline drain, §2.4) |

`forecast_cycle` — NEW columns:
| column | type | notes |
|---|---|---|
| `opened_at` | TIMESTAMPTZ NULL | when the scheduler opened it (provenance) |
| `closed_at` | TIMESTAMPTZ NULL | |
| `reference_tz` | TEXT NOT NULL DEFAULT 'Europe/London' | TZ used only to interpret DATE window bounds (§2.1); group reporting TZ |

### 2.8 Cycle state machine
```
        openCycle (scheduler, idempotent)        closeCycle (scheduler@period_end | admin)
   ∅ ───────────────────────────────────► open ───────────────────────────────────────► closed
                                            │
                                            │ (submissions land while open)
                                            └─ forecast_submission: outstanding ──submit──► submitted
                                                                    outstanding ──skip────► skipped
```
Invariant: there is **at most one `open` cycle per cadence** at any instant (enforced by the scheduler + a partial unique index `UNIQUE (cadence) WHERE status='open'`, NEW). A `closed` cycle never re-opens.

## 3. Versioned submissions (append-only)

### 3.1 Model
`forecast_submission` is *one owner's act of forecasting one account in one cycle* (doc 02 §K), unique on `(cycle_id, forecaster_user_id, company_id)`. `forecast_entry` is *a single versioned estimate* — immutable; a revision inserts a new row and stamps `superseded_by` on the prior. The **current** estimate for a key is the latest non-superseded row; the **full time-series** is retained for accuracy (doc 02 §K).

The **estimate key** (the grain at which versioning supersedes) is:
```
estimateKey = (company_id|branch_company_id, product_variant_id, period_month, scenario_id, source)
```
A new estimate for the same key supersedes the prior for that key only — changing the P50 May figure for SKU X does not touch the P80 May figure or the June figure.

### 3.2 Submit (server) — extends doc 04 §H6Q `submitForecast`
```
submitForecast(owner, acct, cycle, lines, device):       // tx; idempotent on (submission, client_batch_id)
  require authz(create, 'forecast', scope=acct.scope)     // doc 05; data_breadth='own' for agents
  require owner owns acct  (account_manager_user_id|owner_user_id == owner)   // 403 otherwise
  require cycle.status == 'open'                          // else 409 cycle_closed (§2.4 re-queue)
  sub = forecast_submission FOR UPDATE
          WHERE cycle_id=cycle AND forecaster_user_id=owner AND company_id=acct
  require sub exists                                       // generated at open; 404 if not owned-at-open
  for (variant, period_month, scenario, qty, source='manual') in lines:
     require qty >= 0                                      // negatives/blanks normalise to 0 client-side (doc 08 S4)
     prior = currentEntry(estimateKey(acct, variant, period_month, scenario, source))   // latest non-superseded
     if prior != null AND prior.qty == qty: continue       // no-op: don't version an unchanged estimate
     newRow = insert forecast_entry(
        submission_id=sub.id, cycle_id=cycle.id, forecaster_user_id=owner.id,
        channel_id=acct.channel_id, sub_channel_id=acct.sub_channel_id, market_id=acct.market_id,
        company_id=enclosingCustomer(acct), branch_company_id=(acct.is_branch ? acct.id : null),
        product_variant_id=variant, period_month=period_month, scenario_id=scenario,
        qty=qty, source='manual', superseded_by=null)
     if prior != null: prior.superseded_by = newRow.id     // append-only supersession
  sub.status='submitted'; sub.submitted_at=now; sub.device=device
  emit forecast.submitted { cycle_id, forecaster, company/branch, lines:[{variant,period,scenario,qty}], device }
  // consumers: coverage rollup (§4), accuracy projection (§5), audit (doc 05 §5)
```
- **No-op suppression:** an unchanged value is not re-versioned (keeps the time-series meaningful — only genuine revisions appear).
- **Account total vs per-SKU:** `product_variant_id` NULL on an entry = the account total for that month/scenario (doc 02 §K). Capture is per-SKU; an account-total row is only produced by Hyperview/system or an explicit account-level estimate.
- **Idempotency:** the offline queue (doc 08 §0) tags each submit with a `client_batch_id`; the server dedupes a redelivered batch (no double-version). At-least-once delivery, idempotent on `event_id` for the emitted event (doc 03 §3).

### 3.3 Offline submission & late drain
Field use is offline-tolerant (doc 08 §0). A queued submission re-validates server-side on sync (owner-still-owns, cycle-still-open, qty sane). If the original cycle closed before drain:
```
onLateDrain(queuedSubmit):
  current = openCycleForCadence(queuedSubmit.cadence)
  if current != null AND queuedSubmit.targetCycle == current: submitForecast(... current ...)
  else: rebind to current cycle's submission for (owner, acct); set submitted_via_cycle_id=current.id
        // the estimate still lands; provenance records it arrived in a later window
  on owner-no-longer-owns: reject 409 reassigned; surface clear post-sync notice (doc 08 S5)
```

### 3.4 Reading the current vs historical estimate
```
currentEntry(key):    SELECT * FROM forecast_entry WHERE key-match AND superseded_by IS NULL
                      ORDER BY created_at DESC LIMIT 1
historySeries(key):   SELECT * FROM forecast_entry WHERE key-match ORDER BY created_at ASC   // full chain
```
The append-only chain is walkable both ways (`superseded_by` forward; `created_at` order back). `GET /h6q/my-forecasts` (doc 06) prefills S4 with `currentEntry` per (variant, month, scenario); S6 history (doc 08) renders `historySeries`.

## 4. Bottom-up rollup & dual aggregation

### 4.1 The hierarchy
```
account → branch → enclosing customer/wholesaler → segment → sub-channel → channel → market
                                                                       ⟂ (independently) by sales agent
```
This is the canonical H6Q hierarchy (doc 07 Decisions; doc 02 §C/§K). `pipeline_coverage` carries a row **at each level** so the board sums up or drills down, and carries `agent_user_id` so the same atomic numbers re-aggregate by person (doc 02 §K).

### 4.2 Rollup consumer — extends doc 04 §H6Q "Auto-rollup"
The `forecast.submitted` consumer (and `crm.deal.*`, `order.*`, `dispatch.*`, `activation.recorded` consumers — §4.6) recomputes `pipeline_coverage` bottom-up. It is **incremental** for live updates and **fully rebuildable** by replay.

```
onForecastSubmitted(evt):                                 // idempotent on event_id
  affected = distinct (market, period_month, scenario) keys in evt.lines
  for (market, period, scenario) in affected:
     recomputeCoverageTree(market, period, scenario)       // §4.3
```

```
recomputeCoverageTree(market, period, scenario):           // deterministic, replayable
  // 1) atomic leaf rows: current (non-superseded) manual + resolved hyperview per branch/account
  leaves = currentForecastLeaves(market, period, scenario)  // §6 resolves manual-vs-hyperview precedence
  // 2) compute the leaf coverage components from deals/orders/activations
  for leaf in leaves:
     upsert pipeline_coverage(
        level='branch', branch_company_id=leaf.branch, company_id=leaf.company,
        channel_id, sub_channel_id, segment, agent_user_id=ownerAgent(leaf), market, period, scenario,
        forecast_qty       = leaf.qty,
        weighted_pipeline_qty = weightedPipeline(leaf.key, market, period),
        shipped_qty        = shipped(leaf.key, market, period),
        activated_qty      = activated(leaf.key, market, period),
        coverage_pct       = (shipped + weighted_pipeline) / nullif(forecast,0),
        coverage_ex_account_pct = coverageExAccount(leaf.key, market, period, scenario))
  // 3) roll BRANCH → CUSTOMER → SEGMENT → SUB_CHANNEL → CHANNEL → MARKET (org axis)
  for level in [customer, segment, sub_channel, channel, market]:
     upsert pipeline_coverage(level, key) = Σ child rows (forecast, weighted_pipeline, shipped, activated)
            ; coverage_pct recomputed from the summed components (NOT averaged — §4.4)
  // 4) roll the SAME leaves by AGENT (ownership axis), independently
  for agent in distinct ownerAgent(leaves):
     upsert pipeline_coverage(level='agent', agent_user_id=agent, market, period, scenario)
            = Σ leaves WHERE ownerAgent(leaf)==agent
  // 5) WoW: see §4.5
```

### 4.3 Coverage math (canonical — doc 04 §H6Q `coverage`)
For a grouping key:
```
forecast          = Σ currentForecastLeaves.qty under key (resolved manual|hyperview, §6)
weightedPipeline  = Σ over open deal_line under key with deal.expected_close in period:
                       deal_line.qty × pipeline_stage.probability_pct/100
shipped           = Σ order_line.qty_dispatched under key, dispatched in period
activated         = Σ activations bound to key in period (v3 only, §7)
coverage_pct      = (shipped + weightedPipeline) / forecast            // forecast>0 else null/∞-guard
coverage_ex_account_pct = same with the scenario.toggle_basis account filtered out (§5/§ex-cuts)
```

### 4.4 Aggregation invariants (reconciliation)
- **Components sum; ratios recompute.** When rolling up a level, sum the *quantities* (`forecast`, `weighted_pipeline`, `shipped`, `activated`) across children and **recompute** `coverage_pct` from the summed components. Never average child `coverage_pct` (a 0-forecast branch would corrupt a weighted mean).
- **Branch axis ≡ agent axis (the reconciliation guarantee).** Both axes are built from the **same leaf rows**; therefore for any (market, period, scenario): `Σ pipeline_coverage WHERE level='branch'` `==` `Σ pipeline_coverage WHERE level='agent'` on every quantity. This is asserted by a reconciliation test (§9 Acceptance) and is exactly why "every branch maps to an account manager, so branch and agent views reconcile" (doc 04 §H6Q) holds by construction.
- **No double count.** A leaf appears once per axis. The customer line is the sum of its branch lines (`company.parent_party_id`, doc 02 §C); segment rolls many customers; the agent line rolls the leaves that agent owns. A unit is counted once in the org tree and once in the agent tree — never twice within an axis.
- **Idempotent upsert.** `pipeline_coverage` rows are upserted on their full dimension key (`UNIQUE(level, channel_id, sub_channel_id, segment, company_id, branch_company_id, agent_user_id, market_id, period, scenario_id)` — NEW unique key, see §4.7); redelivery overwrites with identical values.

### 4.5 Week-over-week (WoW)
`wow_delta` on a coverage row = current `coverage_pct` (or `forecast_qty`, per the board toggle) minus the value as of the **prior cycle's close**. Computed from the `forecast_entry` time-series (the estimate that was current at the prior cycle's `period_end`):
```
wow(key, asOfCycle):
  nowVal   = coverageComponentsAsOf(key, asOfCycle.period_end)
  priorVal = coverageComponentsAsOf(key, priorCycle(asOfCycle).period_end)
  return { forecast_delta: now.forecast - prior.forecast,
           coverage_delta: now.coverage_pct - prior.coverage_pct }
```
Because `forecast_entry` is append-only with timestamps, "what was current at any past instant" is reconstructable — WoW is a query over history, not a stored snapshot. The board (§8) renders ▲▼ chips (doc 08 S5/S6 pattern).

### 4.6 What rebuilds coverage (consumers)
Per doc 04 §H6Q + doc 03, `pipeline_coverage` is rebuilt by consumers of:
| event | effect on coverage |
|---|---|
| `forecast.submitted` / `forecast.updated` | recompute `forecast_qty` (leaf + rollup) |
| `crm.deal.created/stage_changed/won/lost` | recompute `weighted_pipeline_qty` (probability × deal_line.qty) |
| `order.placed` (incl. scheduled tranches) | future scheduled demand → forward `forecast`/pipeline context |
| `dispatch.created`/`dispatch.delivered` | recompute `shipped_qty` (sell-in) |
| `activation.recorded` | recompute `activated_qty` (sell-through, v3 only §7) |
All idempotent on `event_id`; ordering per `partition_key` only (doc 03 §3). A projection rebuild replays the log into an empty `pipeline_coverage` and reproduces it (doc 01 §3a).

### 4.7 Rollup schema deltas (NEW)
Extends **doc 02 §K** `pipeline_coverage` (additive):
| column | type | notes |
|---|---|---|
| `level` | TEXT NOT NULL | `branch`/`company`/`segment`/`sub_channel`/`channel`/`market`/`agent` — the rollup level of the row |
| `wow_delta` | NUMERIC(9,4) NULL | WoW change (§4.5); unit on `forecast_qty` or pct per board toggle, stored as pct here |
| `forecast_source` | TEXT NULL | `manual`/`hyperview`/`mixed` — which source backed the forecast at this key (§6) |
NEW unique key: `UNIQUE(level, channel_id, sub_channel_id, segment, company_id, branch_company_id, agent_user_id, market_id, period, scenario_id)` (NULLs distinct via `COALESCE` sentinel or partial indexes per level). NEW index: `(market_id, period, scenario_id, level)` for board reads.

## 5. Scenario toggles (P20/P50/P80, ex-cuts)

### 5.1 Scenarios
`forecast_scenario` (doc 02 §K): `type` ∈ {`P20`,`P50`,`P80`}, `name`, `toggle_basis` NULL. P50 is the working default (doc 08 S4). The three are **independent numbers** per (variant, month) — not derived from one another (doc 08 S4 Rules). Capture records all three where the owner provides them; the board switches scenario via `?scenario=` (doc 06).

### 5.2 Ex-cuts (`toggle_basis`)
A scenario row may carry a `toggle_basis` that scopes a **cut** — e.g. `ex_octopus`, `ex_motability`, `inc_motability` (doc 02 §K). The cut is applied at coverage time as a filter on the enclosing account, yielding `coverage_ex_account_pct` alongside `coverage_pct` (doc 04 §H6Q):
```
coverageExAccount(key, market, period, scenario):
  excluded = accountsMatching(scenario.toggle_basis)        // e.g. the Octopus energy_partner party subtree
  forecastEx = Σ leaves under key EXCLUDING excluded
  shippedEx  = Σ shipped under key EXCLUDING excluded
  wpEx       = Σ weightedPipeline under key EXCLUDING excluded
  return (shippedEx + wpEx) / nullif(forecastEx, 0)
```
- The base `coverage_pct` (all-in) and `coverage_ex_account_pct` (one named account removed) are **both materialised** on every coverage row (doc 02 §K), so the board toggles between them with no recompute.
- **Which named accounts are cuttable is data** — the resolution `accountsMatching(toggle_basis)` maps a `toggle_basis` value to a `party` subtree (by `party.external_refs`/segment/explicit list). *(OPEN 13b, doc 07: the exact named accounts that get their own H6Q line / cut — Octopus, Motability — and the default Hyperview-vs-manual precedence for retail; this is a product/finance call, data not code.)*
- Multiple simultaneous cuts (e.g. ex-Octopus **and** ex-Motability) are expressed as a `toggle_basis` value resolving to a multi-account exclusion set; the math is unchanged (the exclusion set grows). The board exposes the toggles configured as `forecast_scenario` rows.

### 5.3 Layer interaction
Scenario/cut toggles are `volume`-layer (units/coverage %). Revenue/margin overlays on a scenario are projected only if the principal holds `commercial`/`profitability` (doc 05 §3) — switching scenario never changes which layers are visible.

## 6. Hyperview source integration

### 6.1 Source model
`forecast_entry.source` ∈ {`manual`,`hyperview`} (doc 02 §K). **Manual** = bottom-up rep estimate (carries `submission_id`); **hyperview** = Prophet retail forecast (no `submission_id`, `submission_id` NULL — doc 02 §K). Hyperview is an upstream integration (doc 07 Decisions, M11/Phase 3); H6Q does not run Prophet (§1.3).

### 6.2 Ingestion
Hyperview publishes model forecasts that land as `source='hyperview'` rows. NEW event (extends doc 03 **Forecast**):
- **`forecast.hyperview.published`** · key `channel+market+period` · `{ market_id, channel_id, sub_channel_id?, company_id?, product_variant_id?, period_month, scenario(P20/P50/P80), qty, model_version, generated_at }` · → insert `forecast_entry(source='hyperview', submission_id=NULL, forecaster_user_id=NULL)`, recompute coverage (§4). Producer: Hyperview integration adapter. Consumers: coverage rollup, audit.

```
onHyperviewPublished(evt):                                 // idempotent on event_id
  require evt.channel resolves to a retail channel          // Hyperview is retail-only (doc 04 §H6Q)
  key = (evt.market, evt.channel, evt.sub_channel, evt.company, evt.variant, evt.period_month, evt.scenario, source='hyperview')
  prior = currentEntry(key)
  if prior != null AND prior.qty == evt.qty AND prior.model_version == evt.model_version: return  // no-op
  newRow = insert forecast_entry(... source='hyperview', model_version=evt.model_version ...)
  if prior != null: prior.superseded_by = newRow.id          // hyperview rows version append-only too
  recomputeCoverageTree(evt.market, evt.period_month, evt.scenario)
```
NEW column on `forecast_entry` (extends doc 02 §K, additive): `model_version TEXT NULL` (Hyperview provenance; NULL for manual).

### 6.3 Precedence (manual vs hyperview)
When both a `manual` and a `hyperview` entry exist for the same coverage key, resolution is **configurable**, default **latest `manual` override else `hyperview`** (doc 02 §K, doc 04 §H6Q):
```
currentForecastLeaves(market, period, scenario):
  for each leaf key (market, channel, sub_channel, company/branch, variant, period, scenario):
     m = currentEntry(key, source='manual')
     h = currentEntry(key, source='hyperview')
     resolved = switch precedencePolicy(channel):            // data-driven, default 'manual_overrides_hyperview'
        'manual_overrides_hyperview' -> (m != null ? m : h)
        'hyperview_only'             -> h
        'manual_only'                -> m
        'show_both'                  -> emit both rows, board renders side-by-side (forecast_source='mixed')
     yield resolved
```
- **Default** (`manual_overrides_hyperview`): a rep's manual estimate, if present, beats the model; absent a manual estimate, Hyperview is the retail line.
- **`show_both`**: the board displays manual and Hyperview as two lines for comparison (doc 04 §H6Q "show both"); `pipeline_coverage.forecast_source='mixed'` flags it; coverage is computed against the policy-resolved line, the other shown for reference.
- `precedencePolicy(channel)` is data (per-channel config); *(OPEN 13b — the retail default precedence — doc 07.)*
- Non-retail channels have no Hyperview source → always `manual`.

### 6.4 Provenance & accuracy
Hyperview entries are scored for accuracy independently (`forecaster_user_id` NULL → attributed to `source='hyperview'` / `model_version`), so manual-rep accuracy and model accuracy are comparable over time (§5 accuracy). The append-only chain retains every model version's estimate.

## 7. Sell-through, overhang & V2/V3

### 7.1 Sell-in / sell-through / overhang (doc 04 §H6Q `sellThrough`)
```
sellThrough(company|branch, channel, period):
  sell_in       = Σ dispatched qty to company/branch in period        // from dispatch (sell-in)
  sell_through  = Σ activations bound to company/branch in period      // from activation (sell-through)
  overhang      = cumulative sell_in − cumulative sell_through         // shipped-not-activated (on-shelf)
```
Materialised in `sell_through` (doc 02 §K): `sell_in_qty`, `sell_through_qty`, `last_shipment_date`, `last_activation_date` per `(company_id, channel_id, period)`. Rebuilt by consumers of `dispatch.*` (sell-in) and `activation.recorded` (sell-through). `overhang` is a computed cumulative (NEW computed/stored field option below).

### 7.2 V2/V3 rule (doc 04 §H6Q V2/V3)
Activation/sell-through math considers **only `serial_unit.generation='v3'`** (prefix `0301`); `v2` (`HYPV-`) are **excluded** from on-shelf/activation calculations — they activate via a legacy path and would otherwise read as forever-on-shelf (doc 02 §G, doc 04 §Serial). So:
```
activatedV3(key, period) = Σ activation a JOIN serial_unit s ON a.serial=s.serial_no
                              WHERE s.generation='v3' AND boundTo(s, key) AND a.activated_at in period
// sell_in counts dispatched units regardless of generation; sell_through and overhang count v3 only.
```
This means overhang for a v2-heavy account is computed on the v3 cohort; v2 units are tracked for genealogy/warranty but not for on-shelf coverage.

### 7.3 Sell-through schema delta (NEW)
Extends **doc 02 §K** `sell_through` (additive):
| column | type | notes |
|---|---|---|
| `overhang_qty` | INTEGER NULL | cumulative sell_in − cumulative sell_through (v3) at period end; materialised for the board |
| `generation_scope` | TEXT NOT NULL DEFAULT 'v3' | which cohort the sell_through/overhang covers (audit of the V2/V3 rule) |

## 9. Forecast accuracy scoring

### 9.1 Model
`forecast_accuracy` (doc 02 §K) holds, per `(forecaster_user_id, company_id, product_variant_id?, period)`: `forecast_qty` (what they said), `actual_qty` (sell-in/sell-through), `error`, `bias`, `mape`. Rebuilt from `forecast_entry` history + dispatch/activation actuals (doc 02 §K). It lets us hold each owner's estimates against reality over time (doc 04 §H6Q).

### 9.2 Which estimate, which actual
- **Forecast taken** = the estimate that was **current at the close of the cycle whose `period_month` matched**, i.e. the owner's committed view of that horizon month at the relevant lock point. Configurable: score against P50 by default (the working scenario); P20/P80 scored separately for distribution calibration.
- **Actual** = the realised quantity for that account/period:
  - against **sell-in** (`order_line.qty_dispatched` to the account in the month) — measures order forecasting; and
  - against **sell-through** (v3 activations bound to the account in the month, §7) — measures end-demand forecasting.
  Both are scored; the board labels which.

### 9.3 Metrics
```
scoreAccuracy(forecaster, company, variant?, period, scenario, actualBasis):
  f = forecastTakenAt(forecaster, company, variant, period, scenario)     // current-at-close estimate
  a = actual(company, variant, period, actualBasis)                       // sell_in | sell_through(v3)
  error = a - f                                                            // signed
  bias  = error                                                           // accumulated/averaged → systematic over/under
  ape   = |error| / nullif(a, 0)                                          // absolute percentage error
  // MAPE accumulates across periods for the (forecaster, company[, variant]) series:
  mape  = mean(ape over scored periods)
  upsert forecast_accuracy(forecaster, company, variant, period,
                           forecast_qty=f, actual_qty=a, error, bias, mape)
```
- **Error** = actual − forecast (signed; per period).
- **Bias** = the running mean of signed error → systematic optimism (−) or pessimism (+).
- **MAPE** = mean absolute percentage error across the owner's scored series (guard `actual=0`: exclude or use sMAPE per config).
- Computed per owner, per account, per period (and optionally per SKU). Aggregatable to owner-level (how good is this rep overall) and account-level (how forecastable is this account).

### 9.4 Rebuild & cadence
- A scheduler scores **closed** periods once their actuals are settled (dispatch + activation lag). Append-only `forecast_entry` makes "what they said at the time" reconstructable, so scoring is **replayable** and never depends on a mutable snapshot.
- Hyperview is scored on the same metrics with `forecaster_user_id=NULL` keyed by `model_version` (§6.4), so model vs human accuracy is directly comparable.
- Surfaced: Flutter S6 (own scope, doc 08); back-office board accuracy panel (any scope per grants). `GET /h6q/accuracy` (doc 06).

### 9.5 Accuracy schema delta (NEW)
Extends **doc 02 §K** `forecast_accuracy` (additive):
| column | type | notes |
|---|---|---|
| `actual_basis` | TEXT NOT NULL DEFAULT 'sell_in' | `sell_in`/`sell_through` — which actual was scored against |
| `scenario_id` | UUID → forecast_scenario NULL | which scenario the estimate came from (P50 default) |
| `model_version` | TEXT NULL | set for Hyperview accuracy rows (forecaster NULL) |
NEW index: `(forecaster_user_id, company_id, period)`, `(model_version, period)`.

## 13. Worked example (end-to-end)

CEF (wholesaler master) with 3 branches; owner Asha owns branch CEF-Leeds; Hyperview publishes a retail line; analyst views the board.

1. **Monday 09:00 UTC — scheduler `openCycle`** for `2026-W23`. Asha (and every owner) gets `outstanding` submissions — one per owned **branch** (CEF-Leeds for Asha; master line is derived). `forecast.cycle.opened` → push to Asha: *"4 accounts due."*
2. **Tuesday — Asha submits** CEF-Leeds from her iPad (offline on a train, queued): P50 `{Home 3.0 / 7.5m / type2: 120 for July, 90 for Aug}`. On reconnect, `submitForecast` versions the estimates (append-only), sets the submission `submitted`, emits `forecast.submitted`.
3. **Rollup consumer** recomputes `pipeline_coverage`: leaf row for CEF-Leeds (branch axis) and for Asha (agent axis) — same numbers; CEF-Leeds rolls into CEF (customer) → wholesaler segment → distributor channel → UK market. `coverage_pct` = (shipped + weighted pipeline) / 120 for July.
4. **Wednesday — Asha revises** July to 140. New `forecast_entry` row; prior `superseded_by` set; coverage recomputes; `wow_delta` reflects the change vs prior cycle close.
5. **Hyperview publishes** a UK retail line for July; `forecast.hyperview.published` lands a `source='hyperview'` row on a retail key (not CEF — CEF is distributor). Default precedence leaves CEF on manual; retail key resolves to Hyperview (no manual override there).
6. **Analyst (volume-only) opens the board**: sees units + coverage % across the hierarchy; drills distributor → CEF → CEF-Leeds → Asha's estimate history; toggles **ex-Octopus** (coverage_ex_account_pct, Octopus filtered); no money anywhere. A **finance** user on the same board additionally sees forecast/shipped **revenue** and **margin** overlays.
7. **Reconcile check**: `Σ branch-axis == Σ agent-axis` for UK/July/P50 (§4.4) — ties.
8. **Period closes (later)**: accuracy scheduler scores Asha's July estimate (140) vs actual sell-in and v3 sell-through → `error/bias/mape`; Hyperview's retail line scored against retail actuals by `model_version`. Asha sees her track record in S6.

## 14. Test strategy (doc 07 §Test strategy)

- **Unit (table-driven, pure):** coverage math (§4.3) incl. 0-forecast guard; ex-cut filter (§5.2); precedence resolution (§6.3) over the policy matrix; accuracy metrics (§9.3) incl. `actual=0`; V2/V3 exclusion (§7.2); WoW from history (§4.5).
- **Aggregation reconciliation (the headline invariant):** generate random leaf forecasts/deals/orders → assert `Σ branch-axis == Σ agent-axis` on every quantity, and customer = Σ branches, segment = Σ customers, etc. (§4.4).
- **Append-only / versioning:** a revised estimate inserts a new row + sets `superseded_by`; `currentEntry` returns the latest; the full chain is retained; a no-op value does not version (§3).
- **Idempotency / replay:** redeliver `forecast.submitted` / `forecast.hyperview.published` twice → identical `pipeline_coverage`; rebuild from an empty projection by replay → byte-identical to live (§4.6, doc 01 §3a).
- **Cycle engine:** re-run `openCycle` same week → no duplicate submissions (§2.2); reassignment mid-cycle moves the outstanding submission (§2.5); late offline drain rebinds to the open cycle (§3.3); at-most-one open cycle per cadence (§2.8).
- **Authz / layers:** capture is own-scope (out-of-scope account → 403); a `volume`-only principal's coverage/export payload carries **no money fields** (absent, not zero) — doc 05 §3; export respects layers.
- **Catalogue-live:** a newly-created `product_variant` appears in `GET /h6q/my-forecasts` with no migration (§1.2.4).

## Acceptance

H6Q (M11) is **done** when:

1. **Cycle open generates outstanding submissions per owned account and notifies owners.** Opening a weekly cycle creates one `outstanding` `forecast_submission` per forecastable owned account/**branch** (master derived by rollup) and emits `forecast.cycle.opened`; owners receive a nudge; re-running open the same week is a no-op (idempotent); at most one `open` cycle per cadence exists.
2. **A rep submits per-account/SKU/scenario from any device and it rolls up bottom-up and re-aggregates by agent — reconciling.** A submission from mobile/tablet/web (offline-tolerant, queued, server-revalidated) versions the estimates and emits `forecast.submitted`; `pipeline_coverage` recomputes account→branch→customer→segment→sub-channel→channel→market **and** by agent; **branch-axis Σ ≡ agent-axis Σ** on every quantity (§4.4), and parent levels equal the sum of their children.
3. **Revising an estimate keeps the prior (append-only history).** A new value inserts a new `forecast_entry` and sets `superseded_by` on the prior; the current estimate is the latest non-superseded row; the full time-series is retained; an unchanged value is not re-versioned.
4. **"Who still owes this week" is visible.** `GET /h6q/outstanding` shows submitted/outstanding/skipped per owner for the open cycle; coverage shows partial vs complete capture.
5. **Coverage / WoW recompute live (no reconciliation, no spreadsheet).** Coverage, `coverage_ex_account_pct` and `wow_delta` are materialised projections rebuilt by event consumers and reproducible by replay; no manual consolidation.
6. **ex-Octopus / ex-Motability are toggles.** A `forecast_scenario.toggle_basis` cut yields `coverage_ex_account_pct` materialised alongside the all-in figure; the board switches with no recompute.
7. **A unit-only viewer sees no money; commercial adds revenue; profitability adds margin.** The same board composes from grants per doc 05 §3; money fields are **absent** from a volume-only payload (never zeroed), including in the export.
8. **Ship-not-activate shows overhang; V2/V3 honoured.** `sell_through` materialises sell-in (dispatch) vs sell-through (v3 activations) and `overhang_qty`; v2 units are excluded from on-shelf/activation math.
9. **Hyperview integrates as a retail source with configurable precedence.** `forecast.hyperview.published` lands `source='hyperview'` rows (versioned append-only); default precedence is latest manual override else Hyperview; `show_both` renders both; H6Q runs no model.
10. **Accuracy scores an owner's past estimates against actuals.** `forecast_accuracy` holds error/bias/MAPE per owner/account/period vs sell-in and v3 sell-through, reconstructed from append-only history; Hyperview is scored comparably by `model_version`.
11. **New catalogue SKUs appear automatically** in the capture surface with no schema/config change.
12. **Output-only export.** The spreadsheet export is read-only, layer-respecting, permission-gated and audited; nothing is ever imported.
